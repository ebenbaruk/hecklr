# Milestone M2: voice and email channels (SC3, SC4, F7-F12)

Status, 2026-10-22: **NOT PASSED yet.** The six seeded faults F7-F12 are each caught, SC4 holds
on the loopback agent in CI, and SC3 holds locally. Four gaps keep the gate open: SC3 was
measured on a 10-core laptop and is not in CI, F10 and the voice CLI matrix were run only
locally (on a merge that was never re-run on `main`), and SC4 over WebRTC is not asserted in CI
(#59), and the local SC4 re-check on an idle machine is pending. The launch checklist (spec, "Launch checklist (M2)") has not started.

Gate M2 (spec, "Waves"): voice SC3, SC4, F7-F12 caught. Workstreams WS9 (#12), WS10 (#26), WS11
(#46, #53), WS12 (#17, #62, #66) and the CLI wiring of voice and email (#32).

## Gate criteria

"Caught" here means the suite comparison is a regression and the fault's own slice
(`catches-fN` tag or expected grader) flips. That is looser than M1's definition (ADR 0020a:
every expected grader's own paired verdict must regress); under M1's rule F12's `resolved`
(2 scenarios) could not reach significance on its own.

## SC4: loopback timing

The networked loopback agent runs in its own process behind the `websocket` PCM adapter on
127.0.0.1. `uv run python examples/voice-loopback/sc4_calibrate.py --calls 10` (load average 4.8;
`examples/acme-voice/RESULTS.md`, PR #46): 840 measurements over 60 calls, none missing,
**worst error 13 ms**. Error = measured − injected; bootstrap 95% CIs over calls.

| Injected latency / barge-in | Latency bias | Latency \|err\| p95 | Barge-in bias | Barge-in \|err\| p95 | Worst |
| --- | --- | --- | --- | --- | --- |
| 300 / 150 ms | +4 ms [+3, +4] | 7 ms [6, 9] | +4 ms [+3, +4] | 7 ms [7, 9] | 12 ms |
| 600 / 300 ms | +3 ms [+3, +4] | 7 ms [6, 8] | +3 ms [+3, +4] | 8 ms [7, 10] | 13 ms |
| 900 / 200 ms | +4 ms [+3, +4] | 8 ms [6, 10] | +3 ms [+3, +4] | 8 ms [6, 9] | 13 ms |

Also: `hecklr calibrate --voice-loopback` on an idle machine (#32) measured worst 4 ms; a
ten-minute call drifts under 5 ms
(`packages/hecklr-voice/tests/test_timing.py::test_sc4_ten_minute_call_has_no_cumulative_clock_drift`).

Tests, all `@pytest.mark.sc4_timing`:
`packages/hecklr-voice/tests/test_driver.py::test_sc4_response_latency_within_20ms_of_injected_delay`,
`::test_sc4_barge_in_reaction_within_20ms_of_injected_reaction`,
`packages/hecklr-adapters/tests/contract/test_voice_contract.py::test_sc4_contract_response_latency_within_20ms_of_injected_delay`
(WebSocket PCM 16 kHz and 24 kHz burst, Twilio, Pipecat protobuf) and
`::test_sc4_contract_barge_in_reaction_within_20ms_of_injected_reaction`,
`examples/voice-loopback/tests/test_sc4_network.py::test_sc4_latency_and_barge_in_within_20ms_over_the_network[300|600|900]`,
`packages/hecklr/tests/test_cli_calibrate.py::test_sc4_calibrate_voice_loopback_measures_within_20ms`.

**CI.** `.github/workflows/ci.yml`, step "SC4 voice timing (serial)" (`pytest -m sc4_timing -p
no:xdist`, ADR 0010b, PR #53), on every PR and push to `main`. Main run 39792057528: 18 passed, 4
skipped. The parallel step skips these tests, because timing under xdist measures the CPU
contention rather than Hecklr.

Caveats:
- **WebRTC is not asserted in CI** (`livekit`, `pipecat-smallwebrtc`): on the shared runner their
  offsets ranged from −242 to +405 ms. Serially on a local machine they pass (21/21, PR #53). #59.
- The CI network test allows 20 ms plus the agent's self-reported lateness (`max_late_ms`); the
  idle `sc4_calibrate.py` run above holds the strict ±20 ms.
- **Local re-verification on a loaded machine.** The serial SC4 step was run locally during the
  WS11/WS12 follow-up work while other agents loaded the machine (load average 15-34; reported
  by that agent, no log kept). It passed 22/22 only on the third
  attempt; the earlier attempts had 2 failures, with a 48 ms error. CI (idle runner) is green. An
  idle-machine local re-run is **pending**. The failures are what ADR 0010b predicts for a shared
  CPU, but until the idle re-run they are not proven to be load alone.
- The Pipecat SmallWebRTC reference bot loses about 110 ms of caller speech (#27).

## SC3: 50 simultaneous calls

`examples/voice-loopback/sc3_load.py --calls 50 100 150` (`examples/acme-voice/RESULTS.md`,
PR #46), on an Apple-silicon laptop with **10 cores**, load average 2.2-5.2:

| Calls | Frame underruns | Worst send lateness | Latency \|err\| p95 | Barge-in \|err\| p95 |
| --- | --- | --- | --- | --- |
| 50 | 0 | 16.4 ms | 3 ms [3, 4] (worst 6) | 3 ms [3, 3] (worst 5) |
| 100 | 0 | 12.4 ms | 4 ms [2, 5] (worst 5) | 2 ms [2, 3] (worst 4) |
| 150 | 0 | 19.6 ms | 5 ms [4, 5] (worst 12) | 3 ms [3, 4] (worst 11) |
| 200 | 33,698 | 92 ms | 31 ms [28, 34] (worst 61) | 42 ms [35, 48] (worst 200) |

At 200 calls the single harness event loop saturates (about 20k frame events/s), not the CPU.
In-process, `packages/hecklr-voice/tests/test_perf.py::test_sc3_fifty_simultaneous_calls_without_underruns`
(`-m perf`, PR #12): 50 calls, 0 underruns, latencies 496-511 ms against 500 ms injected.

Not met as written:
- **Not in CI.** The 4-vCPU runner skips `test_perf.py`, and there is no weekly or release
  performance workflow (spec, "Test layers"). CI runs only a 4-call smoke
  (`examples/voice-loopback/tests/test_bench.py::test_sc3_load_level_reports_transport_health_and_cpu`).
- Measured on 10 cores, not 8, with the loopback agent and synthetic speech (no ASR or TTS model
  in the loop). #55: under local `-n auto` the SC3 test shares the CPU with other workers.
